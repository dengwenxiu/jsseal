# jsseal 先进性与时代定位

> 本文回答"jsseal 处在什么位置、先进在哪"。方法论机制见
> [PRINCIPLES.md](PRINCIPLES.md)；本文讲**时代坐标、理论创新与对比**。

## 1. 时代坐标：JS 反混淆的三个时代

### 1.1 AST 时代（约 2018 起）：静态规则匹配

约 2018 年起，爬虫/逆向社区开始把 AST（Babel）引入 JS 反混淆，代表作
[synchrony](https://github.com/relative/synchrony)、
[webcrack](https://github.com/j4k0xb/webcrack)、
[REstringer](https://github.com/HumanSecurity/restringer)。
范式是**静态规则**：识别结构模式（字符串池/轮转器/分发器）→ 按家族写规则改写。

局限是本质性的：**AST 是语法层，没有语义**。规则假设"这段代码在干什么"，
却从不验证——规则对了就对了，错了就产出错代码，而且无从察觉。它也是**局部**
的：一次 visitor 通行只能看到子树，跨函数、跨作用域的混淆（运行时生成的顺序、
依赖时间调度的轮转）静态规则天然够不着。Google 的
[CASCADE](https://arxiv.org/abs/2507.17691) 论文对此的批评就是：
数百条硬编码 AST 规则难以应对新出现的、多层叠加的混淆。

### 1.2 引擎时代：优化是全局的，前提是语义（jsseal 的起点）

本项目的作者在 AST 时代就有一个判断：**编译器优化理论早就提供了大量自动消除
混淆的手段**——常量折叠、内联、死代码消除、控制流化简。当年的字符串"加密"
几乎都是纯函数，一眼可求值，本可自动替换。AST 时代缺的不是优化技术，而是
**让这些优化"合法"的语义地基**：优化要求你知道代码的行为，而混淆代码的行为
只有跑起来才知道；跑起来又不确定（随机/时间/网络），优化就无从谈起。

jsseal 补的就是这块地基：**在引擎级封闭一切非确定性，把混淆程序连同环境变成
可重放的确定性纯函数**。有了它，"优化"从语法猜测升维成全局语义变换——
不再匹配"长得像混淆的结构"，而是直接求值、观测、然后**证明**改写没有改变
行为。AST 时代的工具是"规则库"，jsseal 是"带验证的优化编译器"。

### 1.3 AI 时代：LLM 让反混淆"变简单"之后

大模型让"看懂一段混淆 JS"变得容易（甚至 Google 已把 LLM+IR 混合方案
[CASCADE](https://arxiv.org/abs/2507.17691) 部署进生产）。这个时代 jsseal
的价值不是替代 AI，而是给 AI 打地基，见 §4。

## 2. 理论创新

### 2.1 纯函数封闭：把非纯程序变成纯函数

环境封闭的本质是：**让所有非纯函数转换为纯函数**——

```
程序 = f(代码, 环境模板, 入口参数, 种子磁带)
```

随机、时间、网络、时钟全部被引擎级拦截录制（guest 不可觉察），重放时逐位
一致。纯函数的行为是确定的、可靠的、可比对的——这是整个体系的理论根基：
**锚库验证之所以可能，是因为封闭后的程序是纯函数**。

### 2.2 不稳定变量与传染阻断：两层语义

封闭带来一个精细问题：`Date.now()` 重放时是确定的（同磁带同值），但它
**语义上**仍是非确定源。jsseal 因此区分两层：

| 层 | 含义 | 处置 |
|---|---|---|
| 确定性 | 同磁带重放逐位一致 | 可录制、可重放、可进锚库 |
| 稳定性 | 语义上是否依赖外部非确定输入 | 不稳定源打"污点"标记 |

**不稳定变量**（种子输出及其一切派生物）被污点传播标记；对它的优化被
**传染阻断**——引擎的 taint 机制（cret 事件 `t=1`）让"感染了不稳定变量的
计算"自动失去常量化资格。换句话说：确定性让我们**能**验证，稳定性标记让
我们**不滥用**验证——把"恰好这次一样"和"语义上必然一样"区分开。

### 2.3 学术坐标：翻译验证 × 确定性重放

jsseal 的验证闭环在学术上有清晰谱系：

- [翻译验证](https://cs.nyu.edu/home/people/in_memoriam/pnueli/pss00.pdf)
  （Pnueli 等，1998；[Necula PLDI'00](https://people.eecs.berkeley.edu/~necula/Papers/tv_pldi00.pdf)）：
  不预先证明变换器正确，而是**每次变换之后事后验证**这一次翻译保持了语义。
  jsseal 的 governor（锚库逐条重放、失败回滚）正是这个范式在反混淆上的实例。
- 确定性录制/重放（record/replay）：让"同输入同输出"成为可依赖的物理事实，
  jsseal 把它做进引擎 C 层且 guest 不可觉察。

这两条线各自成熟，但据我们所知**此前没有被结合起来**：翻译验证传统上依赖
形式化等价检查器（只能处理受控 IR），而 jsseal 用引擎级确定性重放把"等价
检查"变成了黑盒可执行的动作（重放比对输出向量）——代价是只能保证**可观测
行为**等价而非全语义等价（见 PRINCIPLES §7 的单路径覆盖局限），收益是
**任何能跑的 JS 都能验**，不需要先把代码搬到某个形式化 IR 上。

## 3. 对比

| 维度 | AST 规则工具<br>synchrony / webcrack / REstringer | 裸 LLM | LLM+IR 混合<br>CASCADE（Google） | jsseal |
|---|---|---|---|---|
| 改写机制 | 硬编码规则 | 生成式改写 | LLM 定位关键函数 + IR 变换 | 确定性变换 + 锚库验证 |
| 正确性保证 | 无（规则假设成立才对，错了无声产出错码） | 无（错了要靠后续发现，可能一直发现不了） | IR 变换确定，但无行为等价证明 | **每次变换行为逐位验证，失败即回滚** |
| token 成本 | 0 | 高（全量代码过模型） | 高 | 常见混淆 ~0 token，AI 只处理残余 |
| 新混淆适应 | 等社区写新规则 | 强 | 较强 | 写新变换；写不出时锚库也保证不产坏码 |
| 环境语义 | 无 | 无 | 部分（生产环境） | 引擎级：种子/虚拟时钟/网络 VCR/污点/trace |
| 作为 AI 基座 | 否 | — | — | probe/trace 事实 API +（路线图）LLM 驱动变换 |

## 4. AI 时代的四个优势

1. **省 token**：绝大部分常见混淆（字符串池/轮转/CFF/eval 链/JSFuck…）由
   确定性变换无脑清除，AI 不必把几十 KB 的密文池读进上下文——只分析残余。
2. **不犯错的保证，先于验证存在**：jsseal 的等价性是**构造性**的（恒等变换
   + 锚库逐条把关），不需要"验证 AI 有没有改错"这道额外工序。AI 自动流程
   没有这个约束——只能发现错误之后回头修，而**可能一直发现不了**。
3. **AI 分析的基座**：jsseal 是带环境语义的 JS 引擎，能向 AI 输出代码的
   **性质描述**而非只有文本——probe 报告（家族/池明文/网络流/缺环境）与
   trace 事实（调用实参-返回对、污点标记、真实执行序）。AI 基于这些性质
   展开，比盯着混淆文本多出好几个维度。
4. **（路线图）LLM 驱动 jsseal 的变换 API**：AI 提案高层改写（如"把这个
   闭包提出来"），由 jsseal 执行并锚库验证——在**破译的正确性**（锚库兜底）
   与**高层变换的可推理性**（LLM 擅长的部分）之间取得均衡。这是
   "LLM only suggests names" 原则的推广：**LLM 提案，governor 裁决**。

## 5. 路线图：理论已立、工程推进中

### 5.1 近期

- **局部函数纯化（✅ 已落地：`purify-closures` 变换）**：纯函数封闭是文件级的；
  局部函数可能因闭包捕获而不纯。jsseal 感知作用域后用两条等价策略纯化——
  **提升**（单赋值且初始化"位置无关纯"的捕获 → 声明与函数搬移到模块顶层，
  依赖只剩模块级绑定+参数 = top-pure）与**参数化**（会重赋值的捕获 → 前导
  参数显式化，调用点传当前值，与闭包调用时刻读值语义一致）。安全栅栏：
  捕获只读、名字不逃逸、`arguments`/`this` 禁用、参数化调用点同绑定校验。
  下一步：top-pure 函数在全字面量调用点上的**通用求值折叠**（解码器查表的
  泛化，解锁非 obfuscator.io 家族的常量函数折叠）。Date 等封闭后属
  **不稳定变量**，相关优化被传染阻断（§2.2）。
- **LLM 驱动变换 API**（§4.4）。
- **AST 路径锚定**：把强制分支的序号锚定升级为结构锚定，进一步压窄
  单路径覆盖局限。

### 5.2 JSVMP：超集指令集路线（devirtualize）

JSVMP 常被当作"不可解"，我们认为按分层论证这条路线可以走通——**把
"逆 VMP"从玄学问题变成工程问题**，每一段都有成熟方法：

**第 0 层 · 外壳（已具备）**：VMP 样本首先需要解开外层常规混淆
（字符串池/控制流/反调试）才能进入字节码分析——这正是 jsseal 现有能力。
VMP 不是绕过常规反混淆的理由，反而是它的第一个用户。

**第 1 层 · 抽象——设计指令超集**：VMP 的本质是自定义指令集的解释器。
JS 语言特性很少，其语义空间决定的指令数量理论上有限，因此可以设计一个
**超集指令集**（规范 ISA），表达几乎所有 VMP 指令集的语义。这不是空想——
反编译生态早已验证"通用语义层"思想：
[Ghidra 的 P-code](https://github.com/NationalSecurityAgency/ghidra)、
[LLVM IR](https://llvm.org/docs/LangRef.html)、
[RetDec](https://github.com/avast/retdec) 都是为"多源汇入、统一分析"
设计的中间层。

**第 2 层 · 翻译——AI 擅长的部分**：剩下的工作是把自定义字节码转录到
超集指令集。这是格式翻译/语义对照——正是 LLM 的强项。且 jsseal 的引擎
能力为翻译提供**强约束**：分发循环的 trace（执行序 = 取指序列，
cret = 每次运算的实参-返回事实）给出真实指令流，翻译结果可对照指令流
自检，而不是盲译。

**第 3 层 · 反编译——成熟领域的复利**：一旦字节码落在确定的指令集上，
反编译就是成熟领域：lift 到 IR、接入 IDA/Ghidra 类插件生态、或自研
反编译器。此后每个新 VMP 的边际成本只剩"格式翻译"，而**工具与方法论
在确定性指令集上长期复利积累**。

**第 4 层 · 验证——jsseal 独有的收口**：devirtualize 还原出的 JS 产物
同样可被锚库验证——封闭重放原始 VMP 与还原产物，输出向量逐位一致，
则还原的正确性**第一次获得证明**，而不是"看起来对"。

一句话：外层（jsseal 已解）→ 抽象（超集 ISA）→ 翻译（AI + 指令流约束）
→ 反编译（生态成熟）→ 验证（锚库收口）。

> 本节论证的实践底气来自我们的防护侧姊妹项目 [jvmp](https://jvmp.cn)
> （Java VMP 保护，闭源）：种子化 ISA、多解释器实例、N 版本语义、语义诱饵
> 正是我们日常构建与对抗的东西——破盾的路线图，出自造盾者。
